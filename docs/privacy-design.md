# FlightRisk Privacy Design

This document records how FlightRisk handles imagery of people, what is stored and sent and where, and which settings control it. It describes the current code on this branch, including the appearance-only default of the demo launchers and the off-by-default captures. The user-facing policy for the mobile app is `docs/privacy-policy.md`.

## Appearance-only

Appearance-only matching compares people by clothing color, height ratio and re-identification embeddings (OSNet, CLIP ReID) and never runs face recognition.

- Ground station: `VisionConfig.appearance_only` (env `FLIGHTRISK_APPEARANCE_ONLY`, CLI `--appearance-only` and `--with-face` on `python -m flightrisk.dashboard`) controls whether `_init_pipeline` constructs `FaceRecognizer` (`flightrisk/dashboard/app.py`, around lines 1017-1050). When it is true, no `FaceRecognizer` is built and the `insightface_face` signal is disabled. The config default is false, so a ground station embedded some other way (without the `python -m flightrisk.dashboard` launcher) builds the face recognizer. The `python -m flightrisk.dashboard` launcher defaults to appearance-only unless `--with-face` or `FLIGHTRISK_APPEARANCE_ONLY=0` is given, and `scripts/demo_ground.sh` exports `FLIGHTRISK_APPEARANCE_ONLY=1`, so the demo ground station is appearance-only. `/api/status` reports `appearance_only` and the UI shows a badge.
- On the edge, flight sources (`tello`, `fake`) are appearance-only by default: the edge builds no `FaceRecognizer` and sends no face embeddings. Face matching on the edge needs `--with-face` on `edge_device` or `FLIGHTRISK_APPEARANCE_ONLY=0`. The demo launchers set `FLIGHTRISK_APPEARANCE_ONLY=1`.
- Person crops (JPEG, one per detection) and ReID appearance embeddings do leave the edge: each edge sends them to the ground station over the edge WebSocket link, which is token-authenticated with the shared `FLIGHTRISK_EDGE_TOKEN` when that token is set. The demo launchers refuse to start without it, and the ground station refuses a non-loopback bind without it. In appearance-only mode, the default for the `tello` and `fake` sources, no face embeddings are computed or sent. Detections carry the drone id and relative position.
- The edge link is plain `ws://`, not `wss://`. The shared token authenticates the edge but nothing is encrypted in transit, so the link belongs on a private network (the fleet access point or a trusted LAN) and not on the open internet.
- Face and appearance embeddings are computed in process memory only. They are never written to disk. The dashboard and the mobile app never send face embeddings to an analytics or cloud service. There is one exception inside the edge link: when the ground station is not appearance-only and a target photo is set, `flightrisk/dashboard/app.py` (around lines 1569-1574) extracts the target's face embedding and `broadcast_target` sends it, with the ReID embedding, to every connected edge. This does not happen in the default demo configuration, where the ground station is appearance-only, no face recognizer exists and the face embedding is `None`. The edge also sends its own face embeddings back only when face matching is switched on as above.

## Faces at altitude

Faces are not resolvable at search altitude. The system searches from 60 to 120 m, where a person occupies roughly 20 to 60 px in height in the HERIDAL aerial dataset. A face is a few pixels wide at that scale, so face recognition has nothing to work with and appearance-only matching is the honest design, not a downgrade. The face path remains in the code for close-range use (for example the mobile app held at street level) and is off by default for the aerial demo. InsightFace pretrained model packs are licensed for non-commercial research only, which is a second reason not to depend on them.

## Captures

Captures are match snapshots: the full frame, the person crop and a metadata JSON.

- `DashboardConfig.save_captures` defaults to false (env `FLIGHTRISK_SAVE_CAPTURES`). `maybe_save_match_snapshot` (`flightrisk/dashboard/alerts.py`) is a no-op unless it is enabled, `captures/` is created only when a snapshot is actually saved, and the test suite points `CAPTURES_DIR` at a temporary directory. With the defaults, no bystander imagery is written to disk by the capture path. When enabled, the files are ordinary JPEGs that the application does not encrypt.
- Bystander blur and a consent gate for target upload are out of scope for this build. Keeping captures off is the mitigation.

## What is stored and sent, and where

| Data | Where | Behavior |
|---|---|---|
| Face and appearance embeddings | Process memory | Never persisted. Each edge sends ReID appearance embeddings to the ground station, and face embeddings only when face matching is on (see Appearance-only) |
| Match snapshots (frame, crop, JSON) | `captures/` on the ground station | Not written unless `save_captures` is true |
| Match rows (scores, timestamps, reasoning text) | SQLite `flightrisk_sessions.db` (`flightrisk/persistence.py`) | Stored; reasoning and description fields are encrypted only if `FLIGHTRISK_ENCRYPTION_KEY` is set |
| Target photo path and the photo itself | Path in SQLite; photo kept in memory and shown in the dashboard | Stored as given |
| Match crops sent to the browser | Socket.IO to the operator's dashboard as base64 JPEG | Sent to the connected dashboard only |
| Video recordings | `recordings/` (`flightrisk/recorder.py`), only when the operator starts a recording | Not encrypted |
| Crops and reference photo sent to a reasoning model | Local Ollama by default (`flightrisk/reasoning/agent.py`; `OLLAMA_HOST` may point to another machine) | Sent to that host; not started when `--no-llm` is used |
| Reference photo, person crops and typed description sent to a cloud LLM | iOS and Android apps: Anthropic (`https://api.anthropic.com`), via `CloudClaudeLlmBackend` on each platform | Off by default. Sent only when the opt-in toggle (`flightrisk_allow_cloud_llm`) is on, a Claude API key is saved and Cloud Claude is selected. A saved key alone sends nothing. See "Cloud reasoning opt-in on Android" for the Android specifics |
| Commands and status requests from the phone to a ground station | iOS app to the address the user typed in Settings (`ws://`, `http://`, `wss://` or `https://`; the app refuses `ws://` and `http://` unless the resolved address is a local network address, and does not pin certificates for `wss://` and `https://`). Android app to the address typed on the Ground screen (`http://` or `ws://` only, private-network addresses only) | Sent only while the ground link is switched on. The phone sends land, resume-search and detection-profile commands and status requests. It sends no camera frames, crops or reference photo |
| Detections from the Android phone to a ground station's edge port (phone as an edge) | Android app only, to the address typed in Settings (port 9000 by default; `ws://`, private-network addresses only, not encrypted) | Off by default; sent only after a disclosure is accepted, while a search runs and the app is in view. Box positions, confidence scores and, only after the ground asks for video, a small picture of the whole camera view (which can show people). Crops are null by default and no appearance embedding is produced yet, so the ground cannot match these detections to a search target. Needs the ground's edge token for any non-loopback address |
| Ground station address, ground station API key, edge token and Claude API key | iOS and Android apps | iOS: the address is in UserDefaults, and both keys are in the Keychain (this device only, accessible when unlocked). Android: the address and consent flags are in preferences files that backup excludes, and the three secrets are in `EncryptedSharedPreferences` backed by the Android Keystore. Never in plain preferences, files or logs |
| Telemetry logs, metrics and traces | The local Grafana stack (Loki, Prometheus, Tempo volumes), only when `FLIGHTRISK_OTEL_ENABLED=true` | Operator actions, drone communication, flight-safety and pipeline events as numbers, ids and short tokens; secrets redacted; never embeddings, crops, frames or reasoning text. See `observability/README.md` |
| Operator text and the target photo in telemetry | Operator text in the Loki logs; the photo and a thumbnail in `~/.flightrisk/artifacts/targets/` (mode 0700, files 0600), served to Grafana by a 127.0.0.1-only preview server with expiring signed URLs | Only when `FLIGHTRISK_TELEMETRY_CONTENT=1` (off by default in code); text redacted and capped at 500 characters |

The iOS app opens network connections to three kinds of destination, each started by the user (the Android app is described after the iOS paragraphs). The first is the ground station address the user enters in Settings. The second is `api.anthropic.com`, and only after the cloud opt-in. The third is a user-started model download: when you tap the download button for the on-device Gemma model in Settings, the app downloads the model `mlx-community/gemma-2-2b-it-4bit` from Hugging Face (huggingface.co), a third party. No photo, crop, description or location is sent, but Hugging Face necessarily sees the phone's IP address and which model files are requested; what it does with that is governed by its own policy, which this project has not reviewed (`GemmaModelManager.download`, which goes through `defaultHubApi`). The code search that supports this list covers every `URLSession`, `NWConnection` and hub use in `ios/FlightRisk` and `ios/FlightRiskGround/Sources`. The direct Tello link that earlier iOS builds had was removed, so the app no longer talks to a drone itself. On the ground link the iOS app is a console: it receives status from the ground and sends commands. Detections are sent to a ground station by an edge device (an edge process on a computer, or the Android app acting as an edge), not by the iOS app.

The ground link is not encrypted when the address starts with `ws://` or `http://`, which is the normal case on a LAN. The iOS app sets `NSAllowsLocalNetworking` (and no wider App Transport Security exception) so that the HTTP health check works with unqualified and `.local` host names. The WebSocket link uses `NWConnection`, which App Transport Security does not cover, so the app enforces its own local-address policy (`LanAddressPolicy`): a `ws://` or `http://` address is used only if it resolves to a local network address, and the connection goes to the checked address, never to the name. A name that publishes both local and public addresses is used by its local addresses only (the Android policy is stricter and refuses such a name). Cleartext connections prefer a direct path over a system proxy (`preferNoProxies` is only a preference, so a proxy may still be used if the direct connection fails; the API key is sent only after the server's Engine.IO open) and the health check never uses a proxy or the cellular interface. The link belongs on a trusted private network, like the edge link above; away from one, use `wss://` or `https://`, or a VPN that gives the ground station a private-range address (100.64.0.0/10, used by Tailscale, is refused for cleartext). Certificates are not pinned.

The Android app opens network connections to these destinations, each started by the user: the ground station address typed on the Ground screen (plain `http://` and `ws://`, private-network addresses only, never encrypted); the ground station's edge port, only when phone-as-edge is on; `api.anthropic.com`, only after the cloud opt-in; `storage.googleapis.com`, when the user taps "Download Model" for the on-device Gemma model (a plain GET for the model file; no photo, crop, description or location is sent, but Google necessarily sees the phone's IP address and the file requested; what it does with that is governed by its own policy, which this project has not reviewed); and the Tello drone's own Wi-Fi network (UDP) when the user flies a Tello. `CloudPathAuditTest` fails if a new source file opens a connection or names a cloud host. The Android network security config blocks cleartext for the platform HTTP stacks except to loopback names; the ground clients use plain sockets and enforce the private-address rule themselves (`LanAddressPolicy`), refusing a host name when any of its answers is public. The Android app cannot use `wss://`.

**Cloud reasoning opt-in on Android.** The cloud path on Android sends the same data as on iOS: the cropped image of each detected person, the reference photo and the typed description, to Anthropic. It is off by default. The opt-in (`flightrisk_allow_cloud_llm`, a stored Boolean) and the provider choice are in the preferences file `flightrisk_reasoning`, which Android backup and device transfer exclude, so the consent is not restored to another device. Cloud Claude is used only while the opt-in is on, Cloud Claude is selected and a Claude key can be read from the encrypted secret store; the gate is checked at the start of each call and immediately before the request, and opting out, switching provider or removing the key cancels a request in flight. Redirects are not followed and a failed request is not resent. A "Cloud active" indicator shows on the Settings and Search screens. The consent dialog has the same wording as on iOS.

**Phone as an edge on Android.** When the user turns it on (off by default, after a disclosure that is tied to the typed address), the Android app sends the ground station box positions and scores for each frame, at most twice a second and 50 detections per message. It makes and sends no person crops and no face data, and no appearance embedding yet. A thumbnail of the whole camera view is sent only after the ground asks for video. The consent is stored in `flightrisk_ground_link`, which backup excludes. The link is not encrypted and the disclosure says so. This differs from the edge link of a drone edge described under Appearance-only above, which sends crops and appearance embeddings.

The mobile app stores match thumbnails, scores, GPS fixes and timestamps in a local SQLite database on the phone. Nothing in the dashboard or the mobile app sends data to an analytics or advertising service.

The cloud LLM path is the one place images can leave the user's device for a third party. (The Android phone-as-edge mode can also send a small picture of the whole camera view, but only to the user's own ground station and only when that ground asks for video.) It sends the reference photo, the candidate crop (both can show a face) and, for a description comparison, the typed description to Anthropic. It is off by default; see the table row above for the three conditions. The earlier wording of the policy that no biometric data leaves the phone was true of embeddings and templates only. The policy now states both facts.

## Test fixtures

Tests use only synthetic imagery: rectangles and noise arrays generated in code, and the drawn-rectangle fixtures under `tests/fixtures/aerial_tiny/` (t03). No real person images, face datasets or captured footage are committed. Tests that exercise snapshot saving, recording or the session database write only under pytest's `tmp_path`, never into `captures/` or `recordings/`, and tests never contact a cloud LLM or a real drone. HERIDAL images are downloaded by script into a gitignored `datasets/` directory and are not part of the repository.

## Retention

- Embeddings: discarded when the session or process ends.
- Captures: kept until the operator deletes the files in `captures/`; with the default settings none are written.
- Session database rows and recordings: kept until the operator deletes `flightrisk_sessions.db` or the files in `recordings/`. There is no automatic expiry.
- Mobile app: thumbnails, scores and locations stay until the user deletes them in settings or uninstalls the app.
- Cloud LLM: retention after transmission is governed by Anthropic's policy and is outside FlightRisk's control.
- Telemetry: logs, metrics and traces are deleted after 7 days by the Grafana stack (`LOKI_RETENTION_PERIOD` for logs); target-photo artifacts after `FLIGHTRISK_ARTIFACT_RETENTION_DAYS` (default 7), at most 50 kept.
- Deployments that handle real imagery must use filesystem-level encryption, because image files are not encrypted by the application.
